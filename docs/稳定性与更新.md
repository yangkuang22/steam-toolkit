# 稳定性与更新说明

## ★ 会不会把系统搞坏？

**不会。** 原因：

```
SLSsteam 的加载方式:
  Steam 启动 → LD_AUDIT 加载我们的 .so → 修补 Steam 内存
    ↓
  它【只影响 Steam 这一个进程】
    ↓
  崩了最坏结果: Steam 打不开（桌面/游戏模式本身不受影响）
                    ↓
              用 ~/.local/bin/steam-noinject 启动即可
```

**系统启动和 Steam 完全独立**：
- 开机进游戏模式：SteamOS 的 gamescope 会话先启动，Steam 是它的子进程
- 即使 Steam 起不来，你也能切到桌面模式（Steam 设置里或 `steamos-session-select`）
- 桌面环境（KDE/gamescope）不依赖 Steam

## 四层防崩溃保护

### 第 1 层：启动器文件检查（最外层）
```bash
[ ! -s "$LIB1" ] || [ ! -s "$LIB2" ] → 回退普通启动
ldd 检测到缺依赖 → 回退普通启动
```

### 第 2 层：崩溃计数自动降级（新增）
```bash
连续 3 次启动崩溃 → 自动改为【不注入】启动，并弹桌面通知
恢复方法: 注入库或 Steam 更新后自动恢复；也可手动 rm ~/.SLSsteam-crash-count
```
`steam.sh` 会吞掉段错误（退出码还是 0），所以崩溃判断看的是 `console-linux.txt`
里这次启动后新增的 `steam.sh: line N: PID Segmentation fault` 记录，不看退出码。

### 第 3 层：SLSsteam 自身的特征码保护
```toml
SafeMode = false          # 改 true 会让它更保守（功能减少）
OnlinePatterns = false    # 改 true 会尝试在线拉新特征码
```

### 第 4 层：无注入安全网（永远可用）
```bash
~/.local/bin/steam-noinject     # 直接调 /usr/bin/steam
/usr/bin/steam-jupiter          # 系统原版，不经过任何包装器
```

## Steam 自动更新后会怎样？

| 情况 | 结果 | 处理 |
|---|---|---|
| 特征码没变 | 一切正常 | 什么都不用做 |
| 特征码变了（常见） | Steam 能开，但游戏显示"购买" | 跑 `bash scripts/check-after-steam-update.sh --fix` |
| 大版本改动 | 同样，功能失效 | 可能要等上游 SLSsteam-Plus 适配 |

**关键：任何情况下 Steam 本身都能启动**（有 4 层保护）。

### 2026-11-05：SteamOS 3.9.5 后 Steam 随机段错误

- **症状**：桌面模式点一次崩一次；游戏模式开机慢（会自动重试，当天连崩 16 次第 17 次才成功）。
  `coredumpctl info` 栈顶都是 `matchInBuffer ← patternScanAll ← Patterns::init ← la_objopen`。
- **根因**：`patternScanAll` 的边界判断把段结束地址当成闭区间，结束地址恰好等于模块基址的相邻段也被扫描。
  6 份 core 的出错地址都正好是 `steamclient 基址 - 0x801000`（8MB 线程栈 + 4KB 保护页），且读的是该段第一个字节。
- **为什么升级后才出现**：推测 glibc 2.42+ 把线程栈保护页放进了同一个内存映射（`MADV_GUARD_INSTALL`），
  以前保护页是独立的 `PROT_NONE` 段，会被权限过滤掉。这一点没有直接验证。
- **修复**：`src/memhlp.cpp` 改成半开区间（已在 `scripts/slsplus.patch`）。系统升级清掉了 gcc/make，
  所以 `prebuilt/SLSsteam.so` 是在 10-15 的构建上直接改 2 个字节（`0x13cd72`、`0x13cd7c`，`jb` → `jbe`），
  sha256 `aba7572c…`，其余字节完全相同。
- **不要换成 AceSLS 上游版**：它不读 `config.toml`，也没有 Lua 的 `addappid`/`setManifestid`，入库会全部失效。

**现在：253 个 DLC 的极端配置也稳定运行（0 崩溃）。**
